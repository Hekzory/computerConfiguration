# Writing and change descriptions

- Lead with the result. Use plain language, omit filler and repetition, and use lists when they make the information easier to follow. Keep the explanation needed to understand the change.
- Prefer a short, one-line commit subject, without a body or trailers, unless repository conventions or an explicit request require them. Pass the message explicitly with `git commit -m "..."` so command guards can inspect it.
- For public contributions, write titles and descriptions for a reviewer who has not seen the conversation: explain the problem, resulting behavior, and validation, with detail appropriate to the change. Keep private conversation references out of public text. Repository templates and specialized release metadata take precedence; private work MR conventions apply only to work repositories.
